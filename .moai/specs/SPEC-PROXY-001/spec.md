## §A. 배경

Claude Code는 `ANTHROPIC_BASE_URL`로 지정된 **하나의** 엔드포인트만 바라본다. 그래서 한 세션은 한 백엔드에 묶인다. 기존 `moai cc` / `moai glm`은 이 제약 안에서 동작한다 — 설정 파일의 환경변수를 바꾸고 Claude Code를 다시 띄운다.

이 제약 때문에 지금은 할 수 없는 일이 있다. AWS Bedrock의 Claude와 자체 GPU 클러스터의 오픈 모델을 **같은 세션에서** 쓰는 것.

`moai proxy`는 Claude Code가 바라보는 단일 엔드포인트를 로컬 프로세스로 만들고, 그 뒤에서 여러 백엔드로 나눠 보낸다.

Claude Code에 이미 있는 `CLAUDE_CODE_USE_BEDROCK` 네이티브 경로는 Anthropic 형태 모델만 커버한다. Codex와 Copilot은 OpenAI 형태라 그 경로로 갈 수 없다 — 번역 계층이 필요한 이유가 여기서 나온다.

## §B. 범위

### §B.1 포함

1. `moai proxy` 서브커맨드와 그것이 관리하는 **머신(사용자) 범위** 로컬 상주 데몬. 같은 머신의 여러 프로젝트가 데몬 하나를 공유한다
2. 다섯 가지 그룹 타입의 레지스트리: `bedrock`, `codex`, `copilot`, `litellm`, `openai-compatible`. **단 `copilot`은 타입으로만 등록 가능하고 백엔드 어댑터 구현은 v1 범위에서 제외한다** — §H 참조. v1이 실제로 서빙하는 타입은 넷(`bedrock`, `codex`, `litellm`, `openai-compatible`)이다
3. 그룹별 별칭 매핑과 카탈로그 해석
4. 임시 조합(`-g`)과 저장된 세트(`--set`)에 의한 활성 그룹 선택
5. Anthropic `/v1/messages` 호환 클라이언트 표면 (SSE 스트리밍 포함)
6. OpenAI 형태 백엔드가 공유하는 단일 번역 계층
7. 자격 증명 판독 (기존 CLI가 만든 저장소를 읽기 전용으로)

## §C. 요구사항

요구사항은 GEARS 표기를 따른다. `<subject>`는 프록시, 데몬, 카탈로그 등 해당 동작의 실제 주체를 가리킨다.

### 모듈 1 — 데몬 수명주기

데몬의 범위는 **머신(사용자) 단위**다. 프로젝트 단위가 아니므로, 같은 머신의 서로 다른 프로젝트에서 `moai proxy`를 부르면 같은 데몬을 공유한다.

**REQ-PROXY-001** (Event-driven)
**When** 사용자가 `moai proxy`를 실행하고 **해당 머신에** 이미 동작 중인 데몬이 없으면, 프록시는 데몬을 새로 기동하고 참조 계수를 1로 초기화해야 한다(shall).

**REQ-PROXY-002** (Event-driven)
**When** 사용자가 `moai proxy`를 실행하고 **해당 머신에** 이미 동작 중인 데몬이 있으면, 프록시는 새 데몬을 기동하지 않고 기존 데몬에 연결한 뒤 참조 계수를 1 증가시켜야 한다(shall). 호출한 프로젝트 디렉터리가 서로 달라도 마찬가지다.

**REQ-PROXY-003** (Event-driven)
**When** 연결된 세션이 종료되어 참조 계수가 0에 도달하면, 데몬은 스스로 종료해야 한다(shall). 참조 계수는 **머신 전체의 연결 세션 수**를 세며, 프로젝트별로 따로 세지 않는다.

**REQ-PROXY-004** (Ubiquitous)
데몬은 활성 세션이 요청한 부분집합이 아니라 **등록된 전체 그룹 집합**을 상시 메모리에 보유해야 한다(shall).

### 모듈 2 — 그룹 레지스트리와 세트 선택

**REQ-PROXY-005** (Ubiquitous)
레지스트리는 `bedrock`, `codex`, `copilot`, `litellm`, `openai-compatible` 다섯 타입의 그룹을 등록할 수 있어야 한다(shall). `copilot`은 유효한 타입 값으로 남되 백엔드 어댑터는 v1에서 구현하지 않으며(§H), 프록시는 그 타입의 그룹을 REQ-PROXY-021과 같은 형태로 **그룹 단위 비활성** 처리해야 한다(shall).

**REQ-PROXY-006** (Ubiquitous)
그룹은 사용자가 이름 붙인 항목이며, 레지스트리는 **동일 타입의 그룹이 여럿 공존하는 것**을 허용해야 한다(shall).

**REQ-PROXY-007** (Ubiquitous)
각 그룹은 `opus` / `sonnet` / `haiku` / `fable` 별칭을 해당 백엔드의 구체 모델 식별자로 사상하는 별칭 블록을 선언할 수 있어야 하며, 별칭 네 칸을 넘어서는 모델을 직접 지정하기 위한 모델 목록을 추가로 선언할 수 있어야 한다(shall).

**REQ-PROXY-008** (Event-driven)
**When** 사용자가 `-g`로 그룹 목록을 지정하면, 프록시는 그 목록을 이 세션의 활성 그룹 집합으로 삼아야 한다(shall).

**REQ-PROXY-009** (Event-driven)
**When** 사용자가 `--set`으로 세트 이름을 지정하면, 프록시는 설정에 저장된 해당 세트의 그룹 목록을 활성 그룹 집합으로 삼아야 한다(shall).

**REQ-PROXY-010** (Event-driven)
**When** 사용자가 `-g`와 `--set` 중 어느 것도 지정하지 않으면, 프록시는 기본 세트를 활성 그룹 집합으로 삼아야 한다(shall). 이때 기본 세트는 프로젝트 수준 선호(`llm.proxy.default_set`)가 있으면 그것을, 없으면 머신 수준 기본 세트(`sets.default`)를 써서 해석해야 하며(shall), 어느 계층에도 기본 세트가 없으면 사용 가능한 그룹을 나열하고 오류로 종료해야 한다(shall).

> **프로젝트 포인터가 가리킨 세트가 레지스트리에 없을 때의 처리**는 REQ-PROXY-025가 정한다 — 이 요구사항에서 분리되어 나간 독립 동작이다. 이 문단은 안내일 뿐 규범 조항이 아니다.

**REQ-PROXY-011** (unwanted / 검출된 사건)
**When** `-g`와 `--set`이 동시에 지정된 것이 검출되면, 프록시는 어느 한쪽을 임의로 채택해서는 안 되며(shall not), 두 지시가 상충함을 알리고 오류로 종료해야 한다(shall).

### 모듈 3 — 카탈로그 해석

**REQ-PROXY-012** (Ubiquitous)
카탈로그는 모델을 `<group>/<model>` 형태로 이름 지어야 한다(shall). 동일 타입 그룹이 공존할 수 있으므로 타입에 기반한 이름은 사용하지 않는다.

**REQ-PROXY-013** (Ubiquitous) — [HARD] 전방 호환 제약
카탈로그는 최상위 별칭 하나를 단일 배포가 아니라 `{group, model}` 쌍의 **순서 있는 목록**으로 해석해야 한다(shall). 목록의 순서는 활성 그룹 집합의 순서와 같아야 한다.

**REQ-PROXY-014** (Ubiquitous)
요청 라우팅은 REQ-PROXY-013이 산출한 목록의 **첫 항목**을 사용해야 한다(shall). 부하 분산과 장애 전환은 이 SPEC의 범위가 아니다.

**REQ-PROXY-015** (Event-driven)
**When** 클라이언트 요청이 `<group>/<model>` 형태의 모델 식별자를 담고 있으면, 카탈로그는 별칭 해석을 거치지 않고 해당 그룹으로 직접 사상해야 한다(shall).

### 모듈 4 — 클라이언트 표면과 백엔드 번역

**REQ-PROXY-016** (Ubiquitous)
프록시는 Anthropic `/v1/messages` 호환 표면을 노출해야 하며(shall), 여기에는 SSE 스트리밍 응답이 포함되어야 한다.

**REQ-PROXY-017** (Where — 능력 게이트)
**Where** 대상 그룹의 타입이 `litellm`이면, 프록시는 요청과 응답의 본문 형식을 변환하지 않고 중계해야 한다(shall).

**REQ-PROXY-018** (Where — 능력 게이트)
**Where** 대상 그룹의 타입이 `codex`, `copilot`, `openai-compatible` 중 하나이면, 프록시는 **단일한 공유 번역 계층**을 통해 OpenAI 형태와 Anthropic 형태를 상호 변환해야 한다(shall). 타입별로 별도의 번역 구현을 두어서는 안 된다(shall not).

**REQ-PROXY-019** (Ubiquitous)
번역 계층은 스트리밍 응답의 이벤트 열과 도구 호출 블록을 모두 변환해야 한다(shall). 비스트리밍 경로만 변환하는 것은 이 요구사항을 충족하지 않는다.

**REQ-PROXY-020** (Where — 능력 게이트)
**Where** 그룹 타입이 `codex` 또는 `copilot`이면, 프록시는 해당 CLI가 이미 생성해 둔 자격 증명 저장소를 **읽기 전용으로만** 사용해야 하며, 자체 인증 흐름을 수행해서는 안 된다(shall not).

**REQ-PROXY-021** (When — 검출된 사건)
**When** 어느 그룹의 자격 증명 판독 실패가 검출되면, 프록시는 해당 그룹만 비활성으로 표시하고 나머지 그룹의 서빙을 계속해야 하며(shall), 실패한 그룹 이름과 판독을 시도한 위치를 알려야 한다(shall).

### 모듈 5 — 보안 경계

**REQ-PROXY-022** (Ubiquitous)
데몬은 루프백 인터페이스에만 바인딩해야 한다(shall). 외부에서 접근 가능한 인터페이스에 바인딩해서는 안 된다(shall not).

**REQ-PROXY-023** (Ubiquitous)
데몬은 권한 상승을 요구하지 않는 포트에서 수신해야 한다(shall).

**REQ-PROXY-024** (Ubiquitous)
프록시는 백엔드 자격 증명(토큰, API 키)을 **머신 수준 그룹 레지스트리를 포함한 모든 설정 파일**에 기록해서는 안 되며(shall not), 설정 파일에는 경로, 프로필 이름, 그룹 이름, base URL 같은 **참조**만 기록해야 한다(shall).

> "모든 설정 파일"은 버전 관리 대상 여부와 무관하다 — 머신 레지스트리가 git 추적 대상이 아니어도 위 금지가 똑같이 걸린다. 이 문장은 위 조항의 적용 범위를 풀어 쓴 것이지 별도의 규범 조항이 아니다.

### 모듈 2 보충 — 프로젝트 포인터 미존재 처리 (REQ-PROXY-010에서 분리)

아래 항목은 원래 REQ-PROXY-010 본문에 함께 실려 있었으나, 독립적으로 검증 가능한 별개 동작이므로 분리했다. 소속 모듈은 모듈 2(그룹 레지스트리와 세트 선택)이며, 위치만 ID 오름차순 유지를 위해 §C 끝에 둔다.

> **v0.4.0에서 함께 분리했던 2계층 우선순위 조항은 REQ-PROXY-010 본문으로 되돌렸다.** 되돌린 이유는 Tier L 상한(요구사항 25건 / 인수 기준 25건)이다 — 상한은 완화 대상이 아니라 지켜야 할 규범이고, 우선순위 조항은 REQ-PROXY-010이 이미 정하는 "플래그가 없을 때의 기본 세트 해석"과 같은 동작의 연속이므로 되돌려도 동작 하나가 규범 근거를 잃지 않는다. 반면 아래 항목은 그렇지 않다 — 오류로 종료할 것인가 조용히 대체할 것인가는 별개의 관찰 가능한 결정이라 독립 ID를 유지한다.

**REQ-PROXY-025** (unwanted / 검출된 사건)
**When** 프로젝트 수준 선호가 가리키는 세트 이름이 머신 레지스트리에 존재하지 않는 것이 검출되면, 프록시는 머신 수준 기본 세트로 조용히 대체해서는 안 되며(shall not), 그 이름을 찾지 못했음을 알리고 오류로 종료해야 한다(shall).

## §D. 성공 기준

- Claude Code가 `moai proxy`가 띄운 엔드포인트를 통해 정상 대화를 수행한다 (스트리밍 포함).
- 서로 다른 타입의 그룹 둘 이상을 한 세션에서 사용할 수 있다.
- 두 번째 `moai proxy` 호출이 데몬을 추가로 띄우지 않는다. **서로 다른 프로젝트 디렉터리에서 호출해도 마찬가지다** — 머신 범위 결정이 실제로 관찰되는 지점이다.
- 자격 증명 판독에 실패한 그룹이 있어도 나머지 그룹의 서빙이 계속된다.

## §E. 이해관계자 관점

- **사용자**: 백엔드를 바꾸려고 세션을 다시 띄우지 않아도 된다.
- **비용 관점**: 저렴한 자체 GPU 클러스터와 고품질 상용 모델을 같은 세션에서 역할별로 나눠 쓸 수 있다.
- **운영 관점**: 자격 증명이 각 CLI의 저장소에 남고 프록시 설정에는 참조만 남으므로, 설정 파일을 커밋해도 자격 증명이 새지 않는다.

## §H. 제외 항목 (What NOT to Build)

이 SPEC은 아래를 만들지 않는다. 여기 적힌 항목을 구현하는 것은 범위 이탈이다.

### Out of Scope — 클라이언트 표면 확장

- OpenAI 호환 클라이언트 표면 (`/v1/chat/completions` 등). v1의 소비자는 Claude Code 하나다.
- Claude Code 이외 클라이언트를 위한 인증/멀티테넌시.
- 웹 UI 또는 관리 콘솔.

### Out of Scope — 라우팅 지능

- 별칭 배포 목록에 대한 부하 분산 (라운드로빈, 최소 부하 등).
- 오류 발생 시 다음 배포로의 장애 전환.
- 비용 기반 또는 지연 기반 자동 라우팅.
- 응답 캐싱.

> 위 네 항목은 v2 대상이다. REQ-PROXY-013의 목록 구조는 v2를 **가능하게** 하기 위한 것이지 v1에서 사용하기 위한 것이 아니다.

### Out of Scope — 인증 흐름 구현

- Codex를 위한 OAuth device-code 흐름 자체 구현.
- Copilot을 위한 로그인 흐름 자체 구현.
- 토큰 갱신, 만료 처리, 재인증 UI.

> v1은 각 CLI가 이미 만들어 둔 자격 증명을 읽기만 한다 (REQ-PROXY-020).

### Out of Scope — Copilot 백엔드 그룹 구현 (v1 제외, 후속 이관)

- `copilot` 그룹의 **백엔드 어댑터 구현**. v1이 실제로 서빙하는 그룹 타입은 넷이다: `bedrock`, `codex`, `litellm`, `openai-compatible`.
- Copilot 자격 증명 저장 위치 판독.
- GitHub 토큰 → Copilot 토큰 교환 절차.
- Copilot 추론 엔드포인트 호출.

> **제외되지 않는 것**: 그룹 타입 `copilot` 자체는 스키마와 레지스트리 자료 모델에 **유효한 값으로 남는다** (REQ-PROXY-005). 나중에 되살릴 때 스키마를 다시 설계하지 않기 위해서다. `copilot` 타입으로 등록된 그룹은 v1에서 그룹 단위 비활성으로 처리된다.
>
> **제외 근거**: 저장 위치, 토큰 교환 절차, 추론 엔드포인트 세 가지가 모두 공개 문서에서 확인되지 않았다 (research.md §2.4). 이 상태로 구현 일정을 잡으면 조사에 막혀 나머지 네 타입까지 지연된다. **재개 조건**은 세 항목이 모두 답해지는 것이며 — 공개 문서 개선, 또는 실제로 로그인된 Copilot CLI 인스턴스를 가진 사용자의 관찰 근거 제공 — 그때 M3 이후 또는 후속 SPEC으로 착수한다.

### Out of Scope — 어휘 변경

- 에이전트 `model:` 필드의 5-별칭 어휘(`inherit` / `opus` / `sonnet` / `fable` / `haiku`) 변경 또는 확장.
- 새로운 모델 티어 이름 도입.

### Out of Scope — 기존 명령 변경

- `moai cc` / `moai glm`의 동작 변경 또는 폐기.
- 기존 GLM 백엔드 설정(`llm.glm.*`)의 구조 변경.

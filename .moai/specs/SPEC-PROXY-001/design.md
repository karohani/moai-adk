# design.md — SPEC-PROXY-001 설계

> `moai proxy`의 구조적 결정과 그 근거. 여기 적힌 것은 **왜 이 형태여야 하는가**이고, 무엇을 만들 것인가는 `spec.md`, 어떤 순서로 만들 것인가는 `plan.md`에 있다.
> 사실 근거는 `research.md`. 확인되지 않은 항목은 이 문서에서도 확정하지 않는다.

---

## §1. 설계가 풀어야 하는 문제

Claude Code는 `ANTHROPIC_BASE_URL`을 통해 **하나의** Anthropic 호환 엔드포인트만 바라본다. 그래서 백엔드를 바꾸려면 환경변수를 바꾸고 세션을 다시 띄워야 한다. 기존 `moai cc` / `moai glm`이 정확히 그 일을 한다 — `.claude/settings.local.json`의 환경변수를 고쳐 쓰고 `syscall.Exec`으로 `claude`를 띄운다.

이 방식의 한계는 **한 세션이 한 백엔드에 묶인다**는 것이다. AWS Bedrock의 Claude와 자체 GPU 클러스터의 오픈 모델을 같은 세션에서 쓸 방법이 없다.

`moai proxy`는 그 한계를 없앤다. Claude Code가 바라보는 단일 엔드포인트를 **로컬 프로세스**로 만들고, 그 뒤에서 여러 백엔드로 라우팅한다.

Claude Code에는 이미 `CLAUDE_CODE_USE_BEDROCK` 네이티브 지원이 있지만, 그건 Anthropic 형태 모델만 커버한다. Codex와 Copilot은 OpenAI 형태라 그 경로로 갈 수 없다 — **번역 계층이 필요한 진짜 이유가 여기 있다.**

## §2. 프로세스 모델

### §2.1 싱글턴 데몬 + 참조 계수

`moai proxy`를 부르면 두 갈래로 갈린다.

- 이미 실행 중인 데몬이 있으면 → **거기 붙는다.** 참조 계수를 1 올린다.
- 없으면 → **띄운다.** 참조 계수 1로 시작한다.

세션이 끝나면 참조 계수를 1 내린다. **0이 되면 데몬이 스스로 종료한다.**

세션마다 데몬을 하나씩 띄우지 않는 이유는 두 가지다. 포트가 세션 수만큼 필요해지고, 백엔드 연결 풀과 자격 증명 캐시가 세션마다 중복된다.

### §2.2 데몬은 항상 전체 그룹을 물고 있다

데몬은 등록된 **모든** 그룹을 메모리에 올린다. 자기를 띄운 세션이 요청한 부분집합만 올리는 게 아니다.

이 선택은 싱글턴에서 필연이다. 세션 A가 `-g bedrock-us`로 데몬을 띄운 뒤 세션 B가 `-g gpu-cluster-a`로 붙으면, 부분집합만 올렸을 경우 데몬이 B의 그룹을 모른다. 그럼 데몬을 재시작하거나(A를 끊는다) 동적으로 그룹을 밀어 넣어야(재진입 문제) 한다. 처음부터 전부 올려 두면 붙는 동작이 **읽기 전용**이 되고, 이 문제가 통째로 사라진다.

세션별 활성 그룹 집합은 데몬이 **요청 라우팅 시점에** 참조하는 세션 스코프 상태로 다룬다. 데몬이 무엇을 아는가(전부)와 이 세션에 무엇이 보이는가(부분집합)를 분리하는 것이 핵심이다.

## §3. 설정 스키마

### §3.1 위치 결정 — 2계층 (머신 레지스트리 + 프로젝트 포인터)

> **갱신 이력**: 최초 설계는 그룹 레지스트리 전체를 프로젝트 설정 `llm.yaml` 안의 `llm.proxy.*`에 두기로 했다. 그 결정의 전제는 **레지스트리가 프로젝트 설정이라는 것**이었는데, §3.4의 데몬 범위 결정(머신 단위)이 그 전제를 무효화했다. 따라서 아래와 같이 대체한다. 응집도 논거 자체가 틀린 것은 아니지만, 데몬이 여러 프로젝트를 동시에 서빙하는 이상 프로젝트별 레지스트리는 "그 공유 데몬이 어느 프로젝트의 레지스트리를 따라야 하는가"라는 답 없는 질문을 만든다.

설정은 **두 계층**으로 나눈다.

| 계층 | 위치 | 담는 것 | 버전 관리 |
|---|---|---|---|
| **머신 레지스트리 (SSOT)** | `~/.moai/config/proxy-groups.yaml` | `groups` (백엔드 정의, 연결 정보, 자격 증명 **참조**), `sets` (그룹 이름 목록) | 대상 아님 (사용자 홈) |
| **프로젝트 선호** | `.moai/config/sections/llm.yaml`의 `llm.proxy.default_set` | 머신 레지스트리에 정의된 세트 **이름 하나**를 가리키는 포인터 | 대상 (git 추적) |

**머신 레지스트리가 그룹 정의의 단일 원천이다.** 이유는 §3.4의 데몬 범위 결정에서 곧바로 따라 나온다 — 데몬 하나가 여러 프로젝트를 동시에 서빙하는데 레지스트리가 프로젝트마다 다르면, 그 데몬이 어느 레지스트리를 따를지가 임의 규칙이 된다. 머신 단위 SSOT는 그 충돌을 아예 없앤다.

내용상으로도 맞는 자리다. Bedrock 자격 증명, GPU 클러스터 엔드포인트, LiteLLM 게이트웨이 주소는 **개인/머신 인프라**지 프로젝트 자원이 아니다. 같은 사람이 프로젝트 다섯 개를 열어도 백엔드는 그대로다.

**프로젝트가 가질 수 있는 것은 포인터뿐이다.** `llm.proxy.default_set: cheap`은 "이 프로젝트에서 플래그 없이 `moai proxy`를 부르면 `cheap` 세트를 쓰라"는 선호이고, 정의가 아니라 **참조**다. 정의를 복제하지 않으므로 레지스트리 위치를 다시 논쟁할 필요가 없고, 프로젝트마다 다른 기본값을 쓰는 편의는 그대로 남는다.

부수 효과: 프로젝트 쪽 `llm.yaml` 확장은 필드 하나(`llm.proxy.default_set`)로 줄어들지만, **머신 레벨 설정 파일을 읽는 로더가 새로 필요해진다.** 이건 `.claude/rules/moai/core/settings-management.md`의 프로젝트 섹션 5단계 절차와는 다른 작업이다 (그 절차는 `.moai/config/sections/` 대상이다). plan.md §C에 이 구분을 적어 두었다.

### §3.2 그룹 레지스트리

그룹은 **사용자가 이름 붙인 레지스트리 항목**이다. 타입별 싱글턴이 아니다. 같은 타입 그룹이 여럿 공존할 수 있어야 한다 — Bedrock 리전 둘, GPU 클러스터 셋.

```yaml
# ~/.moai/config/proxy-groups.yaml  (머신 레지스트리 — §3.1)
groups:
  bedrock-us:
    type: bedrock
    region: us-east-1
    profile: default            # AWS 프로필 이름 (자격 증명 자체가 아님)
    aliases:
      opus:   us.anthropic.claude-opus-...
      sonnet: us.anthropic.claude-sonnet-...
      haiku:  us.anthropic.claude-haiku-...
      fable:  us.anthropic.claude-...
    models:                     # 별칭 4칸을 넘어서는 직접 지정용 (선택)
      - us.anthropic.claude-...
  gpu-cluster-a:
    type: openai-compatible
    base_url: http://10.0.0.5:8000/v1
    aliases:
      opus:   qwen-3-72b
      sonnet: qwen-3-32b
```

`aliases` 블록은 `llm.glm.models`의 형태를 그대로 따른다. 새 어휘를 만들지 않는다 — 에이전트 `model:` 필드의 5-별칭 어휘(`inherit`/`opus`/`sonnet`/`fable`/`haiku`)는 고정이고, 이 설계는 그 어휘를 **확장하는 게 아니라 소비한다.**

`models` 목록은 별칭 4칸으로 표현되지 않는 모델을 직접 부르기 위한 것이다.

### §3.3 세트

세트는 그룹 이름의 순서 있는 목록이다.

```yaml
# ~/.moai/config/proxy-groups.yaml  (머신 레지스트리 — groups와 같은 파일)
sets:
  default: [bedrock-us, gpu-cluster-a]
  cheap:   [gpu-cluster-a]
```

```yaml
# <project>/.moai/config/sections/llm.yaml  (프로젝트 선호 — 포인터만)
llm:
  proxy:
    default_set: cheap          # 머신 레지스트리의 세트 이름을 가리킨다
```

선택 방법 셋:

| 호출 | 동작 |
|---|---|
| `moai proxy -g a,b` | 임시 조합 |
| `moai proxy --set name` | 머신 레지스트리의 저장된 세트 |
| `moai proxy` | 아래 해석 순서를 따른다 |

**플래그 없이 부를 때의 해석 순서** (§3.1의 2계층 구조에서 파생된 결정):

```
1. 프로젝트 llm.proxy.default_set 이 있으면 → 그 이름의 세트를 머신 레지스트리에서 찾는다
2. 없으면 → 머신 레지스트리의 sets.default
3. 그것도 없으면 → 사용 가능한 그룹을 나열하고 에러로 종료
```

프로젝트 선호가 머신 기본값을 이긴다. 프로젝트별 편의가 이 계층이 존재하는 유일한 이유이므로, 이기지 못하면 있을 필요가 없다. 1단계에서 가리킨 이름이 머신 레지스트리에 없으면 2단계로 조용히 넘어가지 않고 **에러로 종료한다** — 사용자가 가리킨 세트가 사라진 것은 조용히 다른 세트로 대체할 일이 아니라 알려야 할 일이다.

`-g`와 `--set`은 **함께 쓸 수 없다.** 둘 다 활성 그룹 집합을 정하는 지시라서, 동시에 주면 어느 쪽이 이기는지가 임의 규칙이 된다. 임의 규칙을 만드는 대신 거절한다. 라우터의 기존 `--branch` 플래그-서브커맨드 비호환 검사와 같은 형태다.

### §3.4 데몬 범위와 상태 파일 위치 — 결정됨 (머신 단위)

참조 계수와 리스닝 포트를 어디에 기록할지는 **데몬의 범위**를 정하는 결정이라서, 둘 중 하나를 임의로 고를 수 없었다.

| 선택 | 결과 |
|---|---|
| `.moai/state/` (프로젝트 단위) | 프로젝트마다 데몬 하나. 여러 프로젝트를 동시에 열면 데몬도 그만큼 뜸 |
| `~/.moai/proxy/` (머신 단위) | 머신에 데몬 하나. 여러 프로젝트가 공유 |

**결정: 머신(사용자) 단위.** 사용자 확인을 거친 결정이며, 근거는 둘이다.

1. **레지스트리 항목의 성격.** Bedrock 자격 증명, GPU 클러스터 엔드포인트, LiteLLM 게이트웨이 설정은 **개인/머신 인프라**지 프로젝트 범위 자원이 아니다. 프로젝트를 옮겨 다녀도 백엔드는 같다.
2. **싱글턴 설계와의 정합.** §2.1의 싱글턴 데몬 + 참조 계수 구조는 **같은 머신의 여러 프로젝트가 데몬 하나를 공유할 때만** 의미를 갖는다. 프로젝트마다 데몬을 띄운다면 참조 계수는 한 프로젝트 안의 세션 수만 세는 셈이고, 싱글턴이 절약하는 것(포트, 연결 풀, 자격 증명 캐시)의 대부분이 사라진다.

최초 설계가 걱정했던 모순 — "설정은 프로젝트 단위인데 데몬은 머신 단위" — 은 **설정을 머신 단위로 올려서** 푼다. 데몬을 프로젝트별 구성 여럿을 들고 있게 만드는 복잡한 길은 택하지 않았다. §3.1이 그 결과다.

#### 결정에서 따라 나오는 것

| 항목 | 위치 |
|---|---|
| 데몬 런타임 상태 (PID, 리스닝 포트/소켓, 세션 참조 계수) | `~/.moai/proxy/` |
| 그룹 레지스트리 (`groups`, `sets`) | `~/.moai/config/proxy-groups.yaml` (§3.1) |
| 프로젝트별 기본 세트 선호 | `<project>/.moai/config/sections/llm.yaml`의 `llm.proxy.default_set` (§3.1, §3.3) |

**`.moai/state/`는 이 SPEC이 건드리지 않는다.** 이 저장소에서 `.moai/state/`는 계속 프로젝트 범위로 남으며, 프록시 데몬 상태만 머신 범위로 나간다. 프록시가 `.moai/state/`의 다른 용도에 미치는 영향은 없다.

이 결정으로 plan.md M1의 선행 차단이 풀렸다.

## §4. 카탈로그 데이터 모델

### §4.1 이름 규칙 — `<group>/<model>`

`<type>/<model>`이 아니라 **`<group>/<model>`이어야 한다.** 같은 타입 그룹이 여럿 공존하므로 타입으로 이름을 지으면 충돌한다 — Bedrock 리전 둘이 같은 모델을 서빙하면 `bedrock/claude-opus`가 둘을 가리키게 된다. 그룹 이름은 사용자가 붙이므로 유일하다.

예: `bedrock-us/anthropic.claude-opus-5`, `gpu-cluster-a/qwen-3-72b`

### §4.2 [HARD] 전방 호환 제약 — 별칭은 배포 **목록**으로 해석된다

**최상위 별칭 하나는 단일 배포가 아니라 `{group, model}` 쌍의 순서 있는 목록으로 해석된다.**

```
opus → [ {bedrock-us, us.anthropic.claude-opus-...},
         {gpu-cluster-a, qwen-3-72b} ]
```

목록의 순서는 **활성 그룹 집합의 순서**에서 나온다. `-g a,b`로 주면 a의 별칭 매핑이 앞, b가 뒤다. 세트도 마찬가지로 목록에 적힌 순서다.

**v1 동작: 목록의 첫 항목만 쓴다.** 부하 분산도, 장애 전환도 v1에는 없다.

**v2 동작(이 SPEC 범위 밖): 목록 길이가 2 이상일 때 선택 전략(라운드로빈/최소 부하)과 오류 시 장애 전환이 켜진다.**

이 제약이 여기 명시적으로 적힌 이유: **v2가 순수하게 가산적(additive)이어야 하기 때문이다.** v1을 "별칭 → 단일 배포"로 만들면 v2에서 스키마와 내부 자료구조를 둘 다 바꿔야 하고, 그건 마이그레이션이 된다. 지금 목록으로 만들어 두면 v2는 **이미 존재하는 목록을 소비하는 새 라우팅 로직**일 뿐이고, 스키마는 손대지 않는다.

구현 시 지켜야 할 형태:
- 해석기의 반환 타입은 처음부터 슬라이스다. 단일 값을 반환하고 나중에 슬라이스로 바꾸면 호출부가 전부 깨진다.
- v1 라우팅은 그 슬라이스의 인덱스 0을 읽는 **한 줄**이어야 한다. 그래야 v2에서 그 한 줄만 전략 호출로 바뀐다.
- 설정 스키마는 v2가 도래해도 **바뀌지 않는다.** 목록은 활성 그룹 집합에서 파생되지, 설정에 직접 적히지 않는다.

### §4.3 해석 순서

```
클라이언트 요청의 model 필드
  ├─ "<group>/<model>" 형태 → 해당 그룹으로 직접 지정 (목록 길이 1)
  └─ 별칭 (opus/sonnet/haiku/fable) → 활성 그룹 순서대로 배포 목록 구성 → v1은 [0]
```

## §5. 번역 계층

### §5.1 클라이언트 표면 (v1)

v1의 소비자는 **Claude Code 하나**다. 그래서 프록시가 노출하는 것은 Anthropic `/v1/messages` 호환 표면이고, **SSE 스트리밍을 포함한다.** 스트리밍은 선택이 아니다 — Claude Code가 스트리밍으로 말한다.

OpenAI 호환 클라이언트 표면은 v1에 없다 (spec.md 제외 항목).

### §5.2 백엔드별 번역 부담

`research.md` §4에서 나온 비대칭이 그대로 구조가 된다.

```
                          ┌─────────────────────────────┐
Claude Code ──/v1/messages─→│  moai proxy (loopback)      │
                          │                             │
                          │  litellm  ──── 통과 ────────→ (번역 없음)
                          │  bedrock  ──── 얇은 사상 ───→ Converse/ConverseStream
                          │                             │
                          │  codex     ─┐               │
                          │  copilot    ├─ 공유 번역기 ─→ OpenAI 형태
                          │  openai-compatible ─┘        │
                          └─────────────────────────────┘
```

**OpenAI 형태 백엔드 셋이 번역기 하나를 공유한다.** 셋을 각각 만들면 SSE 재구성과 tool_use 조립 로직이 세 벌 생기고, 버그도 세 벌 생긴다.

> **v1 범위 주의**: `copilot`은 v1 구현 범위에서 빠졌다 (research.md §2.4, spec.md §H). 위 그림에서 `copilot` 가지는 **설계에는 남아 있되 v1에서는 연결되지 않는다.** v1에서 공유 번역기를 실제로 소비하는 타입은 `codex`와 `openai-compatible` 둘이다. 소비자가 둘로 줄었다는 이유로 타입별 구현으로 되돌아가면 안 된다 — 번역기는 처음부터 **소비자 수와 무관하게 하나**여야 하고, 나중에 `copilot`이 세 번째 소비자로 붙을 때 번역 계층을 손대지 않아야 한다.

번역기가 실제로 하는 일은 두 가지에 몰려 있다:

1. **SSE 이벤트 열 재구성** — OpenAI의 `data: {choices[].delta}` 청크를 Anthropic의 `message_start` / `content_block_start` / `content_block_delta` / `content_block_stop` / `message_delta` / `message_stop` 열로 바꾼다. 청크 경계가 1:1이 아니라서 상태 기계가 필요하다.
2. **tool_use 블록 변환** — OpenAI `tool_calls`는 인자가 문자열화된 JSON이고 스트리밍 중 조각나서 온다. Anthropic `tool_use`는 구조화된 `input` 객체다. 조각을 모아 파싱해야 한다.

### §5.3 자격 증명 판독의 취약성 격리

`codex`와 `copilot`은 **다른 CLI가 만든, 문서화되지 않은 자격 증명 저장소를 읽는다** (research.md §2.3, §2.4). 그 포맷은 우리 통제 밖이고 상대가 언제든 바꿀 수 있다.

따라서 판독기는 **격리된 지점**이어야 한다:
- 판독 실패가 프록시 전체를 죽이면 안 된다. 해당 그룹만 비활성으로 표시하고 나머지는 계속 서빙한다.
- 실패 메시지는 "어느 그룹이, 어느 경로에서, 무엇을 못 읽었는지"를 말해야 한다. 사용자가 해당 CLI로 다시 로그인하면 되는 문제인지 판단할 수 있어야 한다.
- Codex는 저장 위치가 **둘**이다 — 평문 `~/.codex/auth.json` 또는 OS 자격 증명 저장소. 판독기는 둘 다 시도해야 한다.

#### Codex 평문 파일의 관찰된 스키마 (research.md §2.3 로컬 관찰)

평문 경로의 필드 구조는 로컬 관찰로 확보했다: 최상위에 `auth_mode` / `OPENAI_API_KEY` / `tokens` / `last_refresh`, `tokens` 하위에 `id_token` / `access_token` / `refresh_token` / `account_id`. 파일 권한은 `0600`.

**이 스키마를 확정된 계약으로 취급하면 안 된다.** 관찰은 한 인스턴스에서 이뤄졌고, 그 머신의 바이너리는 문자 그대로의 `codex`가 아니라 `opencodex`였다 (research.md §2.3 단서). 판독기 구현 전에 **실제 공식 OpenAI Codex CLI 설치본에 대해 검증**해야 한다.

이 불확실성이 판독기 설계에 남기는 요구는 셋이다:
- 파싱은 **관대해야 한다.** 모르는 필드가 있어도 실패하지 않고, 필요한 필드가 없을 때만 실패한다. 스키마 전체 일치를 요구하면 상대가 필드 하나를 더할 때 깨진다.
- `auth_mode`를 **분기 신호로 읽는다.** 관찰된 값은 `"chatgpt"`였고 그 인스턴스의 `OPENAI_API_KEY`는 `null`이었다. 다른 값(API 키 인증 등)의 저장 형태는 관찰하지 못했으므로, 모르는 `auth_mode`를 만나면 추측하지 말고 그 그룹을 비활성으로 표시한다.
- 실패 메시지는 위 격리 규칙대로 **어느 경로에서 무엇이 없었는지**를 말한다. "codex 인증 실패"만으로는 사용자가 재로그인으로 풀 문제인지 스키마 변경인지 구분할 수 없다.

### §5.4 Bedrock — Converse 대 InvokeModel (미결)

Converse는 모델 무관 통합 형태라 코드가 한 벌로 끝난다. InvokeModel은 Anthropic 네이티브 페이로드를 그대로 넘길 수 있어 번역이 더 얇아질 수 있다.

`research.md`가 Converse의 통합성과 tool use 지원은 확인했지만, **Anthropic `/v1/messages` 스키마와의 필드 단위 차이는 대조하지 않았다.** 그 대조 없이 어느 쪽이 더 얇은지 단정할 수 없다.

**미결 — Bedrock 경로(Converse vs InvokeModel).** 필드 대조표를 만든 뒤 결정한다. plan.md §B에 미해소 항목으로 등록되어 있다. **M1(설정 스키마 + 카탈로그)은 이 결정에 의존하지 않으므로 이 항목은 M1을 막지 않는다** — 대조표는 Bedrock 어댑터를 실제로 구현하는 **M2 안에서** 만들고 그 자리에서 결정한다.

> **결정 기록 (2026-08-20) — 이 항목은 "미해결 질문"이 아니라 "이월이 승인된 항목"이다.** 오케스트레이터가 `AskUserQuestion` 라운드를 돌려 사용자의 명시적 승인을 받았고, 결과는 **M2(Bedrock 어댑터 마일스톤)로의 이월 확정**이다(즉시 조사 대안은 선택되지 않았다). 이것은 조사 결과가 아니라 **해소 시점에 대한 사용자 승인 결정**이다. 근거로 기록된 것: Converse가 유력 경로라는 점은 이미 확인되었고 남은 것은 필드 단위 대조표뿐이므로, 대조표는 착수 전에 따로 만들지 않고 **Bedrock 어댑터 구현 작업의 일부로** 만든다. 위 문단의 "미결" 서술은 **무엇이 아직 대조되지 않았는지**를 계속 기록하기 위해 그대로 둔다 — 지우지 않는 것이 이 결정 기록의 전제다. 대응 표식: plan.md §B.2 / research.md §5.2의 Bedrock `CLARIFICATION-DEFERRED` 행(v0.4.0에서 표식 형식이 전환됨).

## §6. 보안 경계

세 가지가 타협 불가다.

1. **loopback 전용 바인딩.** 데몬은 `127.0.0.1`에만 바인딩한다. 데몬은 여러 백엔드의 유효한 자격 증명을 들고 있으므로, 외부 인터페이스에 노출되면 그 자격 증명 전부에 대한 인증 없는 대리 접근을 열어 주는 셈이 된다.
2. **권한 상승 불필요.** 포트는 비특권 대역이어야 한다. 1024 미만 포트는 쓰지 않는다.
3. **자격 증명은 설정 파일에 절대 쓰지 않는다 — 참조만 쓴다.** 이 규칙은 **두 계층 모두**에 걸린다.
   - `<project>/.moai/config/sections/llm.yaml` (git 추적): 세트 이름 포인터만.
   - `~/.moai/config/proxy-groups.yaml` (git 추적 대상 아님): 그래도 **참조만** 쓴다 — 경로, AWS 프로필 이름, 그룹 이름, base URL. 토큰과 API 키 자체는 들어가지 않는다.

머신 레지스트리가 버전 관리 대상이 아니라는 사실이 이 규칙을 느슨하게 만들지 않는다. 이유는 git 유출만이 아니기 때문이다 — 자격 증명은 각 CLI가 이미 자기 저장소에 두고 있고(`~/.codex/auth.json`, AWS 프로필), 그것을 설정 파일에 복사하면 **원본과 사본의 만료 시점이 어긋나는** 두 번째 진실 원천이 생긴다. 사용자가 해당 CLI로 재로그인해도 우리 사본은 낡은 채로 남는다. 참조만 두면 갱신은 원본 쪽에서 한 번만 일어난다.

3번은 §3.2의 스키마에 이미 반영되어 있다. `bedrock-us` 그룹이 `profile: default`를 갖는 것은 "AWS 프로필 이름"이지 자격 증명이 아니다.

## §7. 이 설계가 의도적으로 하지 않는 것

- **자체 OAuth 흐름을 구현하지 않는다.** codex와 copilot 로그인은 각 CLI가 이미 하는 일이고, v1은 그 결과물을 **읽기만** 한다. 로그인 흐름을 우리가 다시 구현하면 토큰 갱신, 만료, 재인증 UI가 전부 우리 책임이 된다.
- **에이전트 `model:` 어휘를 건드리지 않는다.** 5-별칭(`inherit`/`opus`/`sonnet`/`fable`/`haiku`)은 고정이다.
- **v1에 라우팅 지능을 넣지 않는다.** §4.2의 목록 구조는 v2를 **가능하게** 하려는 것이지 v1에서 쓰려는 게 아니다.
